## Ownership
- **Canonical schema:** `_Shared/schemas/zoning-envelope.schema.json`
- **Owner:** the Project 1 session (built during 1B). It publishes the schema here early, before 1B's UI work.
- **Consumers:** the Project 3 session reads it from here and copies it into each app's `/schemas/`.
  If it does not exist yet, Project 3 drafts `_Shared/schemas/zoning-envelope.schema.draft.json` from its own
  PROMPT and logs it below. Project 1 reconciles the draft into the canonical file.
- Breaking changes: bump `version` in the schema and add an entry to the change log.

## Required fields (from both prompts)
Lot polygon (local coords + EPSG:2263 reference), max FAR by use, base height min/max, max building height,
setback planes (distances & heights), yard depths, lot coverage, sky exposure plane params where applicable,
citations per field, `assumptions[]`, provenance (dataset/version/fetch time), SAMPLE / SIMPLIFIED flags.

## Consumer notes (v1.0.0)
- Validate with any JSON Schema 2020-12 validator (Ajv 2020 in JS). Units: all lengths/heights in feet, areas in sf, FAR as ratio, coverage as percent.
- Treat `status: manual|needs_input` as "do not generate geometry for this constraint; show to the user".
- Example envelopes from real lots (generated by 1B from verified rules + PLUTO 26v2, schema-valid, `flags.sample:false`, `simplified:true`): `_Shared/schemas/examples/r7a-interior-152-attorney-st.json`, `r6a-interior-287-convent-ave.json`, `r7a-corner-270-east-3-st.json` (2026-10-26). Values with status manual/needs_input are null by design.

## Browser handoff: Site Brief → Massing Studio (added 2026-10-30, manager)
"Open in Massing" in 1B sends the envelope straight to 3A in the same browser. No server and no size limit.
1. 1B opens `${MASSING_URL}/?from=site-brief` with `window.open(url, "wxy-massing")`. Keep the opener; don't pass `noopener`.
   `MASSING_URL` = `process.env.NEXT_PUBLIC_MASSING_URL ?? "http://localhost:3301"`.
2. 3A, when the query has `from=site-brief` and `window.opener` exists, posts `{ type: "wxy:massing-ready", version: 1 }` to the
   opener with targetOrigin `"*"`. This message carries no data. It re-posts every 500 ms until it gets an envelope, for up to 10 s.
3. 1B listens for `wxy:massing-ready` only when `event.origin` matches `MASSING_URL`'s origin and `event.source` is the window it opened.
   It replies once to that window, with targetOrigin set to the Massing origin:
   `{ type: "wxy:envelope", version: 1, envelope: <ZoningEnvelope>, source: { app: "site-brief", address: string, bbl: string | null } }`.
4. 3A accepts `wxy:envelope` only when `event.origin` matches
   `process.env.NEXT_PUBLIC_SITE_BRIEF_URL ?? "http://localhost:3101"`. It then validates the envelope against the schema as usual,
   loads it as a non-sample site and shows "Loaded from Site Brief: <address>". On timeout or an invalid envelope it shows plain
   guidance: "Couldn't receive the lot from Site Brief. In Site Brief, use Download JSON, then Load envelope here."
5. Both sides remove their listeners when they're done. If the popup is blocked (`window.open` returns null), 1B says so and
   points to Download JSON.
